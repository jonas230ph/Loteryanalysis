# PCSO iOS Mobile App Design

Date: 2026-05-18

## Goal

Build a native SwiftUI iPhone app that shows PCSO lottery results and analysis generated by the existing Python scraper and analyzer. The app should be useful as a results and historical-analysis companion, while keeping scraping and data processing outside the mobile client.

The first version will include results viewing and analysis. It will not run the scraper on-device and will not include accounts, notifications, payments, or App Store production deployment work.

## Recommended Approach

Use a small Python mobile API as the boundary between the SwiftUI app and the current scraper/analyzer outputs.

```text
PCSO website
  -> pcso_lottery_scraper.py
  -> pcso_results.json
  -> analyze_pcso_results.py
  -> analysis_outputs/*.csv
  -> mobile_api JSON endpoints
  -> SwiftUI app
```

This keeps the fragile PCSO scraping flow on a backend, where dependencies, anti-bot behavior, scheduling, logs, and fixes are easier to manage. The iOS app consumes clean JSON and can focus on presentation, filtering, and navigation.

## Project Structure

```text
my_scraper/
  pcso_lottery_scraper.py
  analyze_pcso_results.py
  mobile_api/
    app.py
    services/
      results_service.py
      analysis_service.py
  ios_app/
    PCSOLotto/
      PCSOLottoApp.swift
      Models/
      Services/
      Views/
```

`mobile_api/` owns HTTP endpoints and conversion from local JSON/CSV files into mobile-friendly payloads. `ios_app/` owns the SwiftUI project and should not import or duplicate Python logic.

## Mobile Features

### Results

The Results screen shows latest PCSO draws in a searchable/filterable list. Each row should show the game name, combination, draw date, jackpot, and winners. The screen should support selecting a game to drill into recent history.

### Game Detail

The Game Detail screen shows the selected game's latest draw, recent draw history, jackpot and winner information, and a path into analysis for that game.

### Analysis

The Analysis screen shows historical summaries from `analysis_outputs/`, including number frequency, odd/even patterns, and sum statistics. The first implementation can use simple native lists and compact chart-like rows rather than complex chart rendering.

### Suggestions

The Suggestions screen shows generated combinations from `possible_winning_numbers_by_game.csv`, including combination, sum, odd/even pattern, historical frequency score, and basis. The screen must include a clear disclaimer that suggestions are based on historical patterns and do not predict winning numbers.

### Settings and Info

The app should show the latest data refresh timestamp if available and include a concise disclaimer about lottery randomness and responsible use.

## Backend API

The mobile API should expose these initial endpoints:

```text
GET /api/results
GET /api/games
GET /api/games/{game}/results
GET /api/games/{game}/analysis
GET /api/suggestions
```

Responses should be JSON-only and shaped for Swift decoding. Endpoint failures should return structured errors with a message and HTTP status code.

## SwiftUI Architecture

Use a small MVVM-style structure:

```text
Models/
  LottoResult.swift
  GameAnalysis.swift
  Suggestion.swift

Services/
  APIClient.swift
  LotteryRepository.swift

Views/
  ResultsView.swift
  GameDetailView.swift
  AnalysisView.swift
  SuggestionsView.swift
```

`APIClient` handles HTTP transport and JSON decoding. View models or lightweight observable repositories hold loading, loaded, empty, and error states. Views remain mostly declarative and do not know backend file formats.

## Error Handling

The backend should handle missing `pcso_results.json`, missing CSV analysis outputs, invalid file content, and unknown game names. The SwiftUI app should show retryable error states instead of crashing or silently emptying screens.

The iOS app should support a configurable base URL for local development. Production deployment is deferred from this first version and should be designed after the API is hosted.

## Testing

Backend tests should cover JSON/CSV loading, endpoint response shapes, missing-file behavior, and game filtering.

Swift tests should cover model decoding and API-client error handling. UI verification should include the main screens in loading, loaded, empty, and error states once the app scaffold exists.

## Out of Scope For First Version

- On-device scraping
- User accounts
- Push notifications
- Saved/favorite number sets
- App Store submission
- Production hosting automation
- Guaranteed prediction or winning-number claims
